# 企业人事管理系统项目说明

## 1. 项目背景

本项目是企业级开发实践课程的学习项目，面向单个企业内部的人事管理场景，基于 RuoYi-Vue 后端与 RuoYi-Vue3 前端进行业务扩展。

项目通过员工档案、部门与职位、薪资、考勤和请假等业务，练习从需求分析、系统设计到编码、测试和版本交付的软件开发过程，并为课程设计报告提供素材。

本项目用于本地学习和演示，不作为生产环境的人事系统，不使用真实员工及薪资数据。

## 2. 项目目标

### 2.1 功能目标

完成以下六项课程必需功能：

1. 员工信息管理。
2. 部门与职位管理。
3. 薪资计算。
4. 考勤打卡。
5. 请假审批。
6. 权限分级管理。

实现员工和管理人员之间的基本业务闭环：HR 建立员工档案并关联账号，员工查看个人信息、打卡、申请请假及查询工资，相关管理人员完成维护和审批。

### 2.2 学习目标

- 理解 Java 实体、接口、实现类及异常处理在项目中的用途。
- 理解 Spring Boot 项目的请求处理和分层结构。
- 理解关系型数据库设计、约束和 MyBatis 数据访问。
- 理解 Vue 页面如何调用后端接口并展示结果。
- 区分身份认证、操作权限和数据权限。
- 掌握需求、设计、实现、验证、审查和 Git 交付的基本流程。
- 学会使用 AI 辅助开发，并能够解释和验证所采用的代码。

## 3. 使用角色

| 角色 | 主要职责 |
|---|---|
| 系统管理员 | 管理账号、角色、菜单和权限；处理审批例外；具有全部业务操作权限 |
| HR | 维护员工档案、工资及考勤；查看全公司请假记录；审批部门负责人的请假 |
| 部门负责人 | 查看直属部门员工的基础档案和请假记录，审批分配给自己的申请 |
| 员工 | 查看本人档案、考勤和已发布工资单，进行上下班打卡及请假申请 |

业务角色可以组合，但审批流程必须禁止申请人审批自己的申请。

## 4. 功能范围

### 4.1 员工信息管理

HR 维护工号、姓名、部门、职位、入职日期、在职状态和备注。

工号唯一，员工档案与登录账号一对一关联。员工只能查看本人档案。离职通过状态记录，保留历史档案。

### 4.2 部门与职位管理

复用若依现有部门和岗位管理功能。课程中的“职位”对应系统现有“岗位”。

每个员工归属一个部门、一个职位。部门负责人需关联实际登录账号，不能仅以负责人姓名确定审批权限。

### 4.3 薪资计算

月度工资按以下公式计算：

应发金额 = 基本工资 + 津贴 + 奖金 − 扣款

各项金额由 HR 维护，计算结果保留两位小数。工资单在草稿状态下可编辑，发布后只读。员工只能查看本人已发布工资单。

不自动计算个税、社保或考勤扣款，不进行银行发薪。具体金额校验规则在需求与设计阶段确定。

### 4.4 考勤打卡

员工在网页点击上班、下班打卡，记录时间由后端提供。

每天各允许一次，必须先上班后下班，不支持跨日班次。HR 可以补录或更正考勤，并填写原因。员工只能查看本人考勤。

不接入定位、硬件设备或外部考勤平台。

### 4.5 请假审批

提供事假和病假，按整天申请，天数按照包含首尾日期的自然日计算，不处理节假日，也不自动影响工资。

支持提交申请、撤回待审申请、批准和驳回；驳回必须填写原因。

审批规则：

- 普通员工的申请由所属部门负责人审批。
- 部门负责人的申请由 HR 审批。
- HR 的申请或部门没有负责人时，由管理员审批。
- 禁止自审；候选审批人是申请人时，转交其他管理员。
- 没有可用审批人时，提示先完善配置。
- 提交时保存所属部门和审批人，调岗不改变已提交申请。
- 部门负责人范围只包含直属部门，不自动包含下级部门。
- 待审或已批准申请不能发生时间重叠。

存在多名可用 HR 或管理员时的审批人选择方式，在详细设计中明确。

### 4.6 权限分级管理

复用若依登录、角色、菜单和操作权限机制，并增加业务数据范围检查。

员工只能访问本人业务数据。负责人只能查看本部门基础档案与请假信息。HR 管理全公司业务数据。管理员具有全部操作权限。

权限必须由后端校验，不能仅依靠前端隐藏按钮。

## 5. 技术与项目组织

- 后端：Java 17、Spring Boot、Spring Security、MyBatis。
- 数据库：MySQL 8。
- 缓存：Redis 协议服务，本地使用 Memurai。
- 前端：Vue 3、JavaScript、Element Plus、Vite。
- 构建与版本管理：Maven、npm、Git、GitHub。

后端和前端保留独立 Git 仓库，均保留原有提交历史、MIT 许可证及官方 upstream 远程。

项目文档统一维护在后端仓库 `doc/course/`，前端 README 提供链接。数据库变更使用独立增量 SQL，不覆盖若依原有初始化脚本。

数据库密码通过环境变量提供，不写入提交到 Git 的配置。

## 6. 开发方式

采用文档先行、分步实现的方式：

项目说明 → 需求说明 → 设计说明 → 实施与测试计划 → 功能开发 → 验收与交付。

用户手动编辑、运行和提交；AI 协助梳理需求、解释代码、提出方案和检查结果。

每个开发任务按以下顺序执行：

说明目的 → 阅读参考代码 → 手动修改 → 理解关键代码 → 验证 → 检查差异 → 提交。

先手写员工功能的一条完整调用链。后续可使用代码生成器减少重复工作，但生成的代码仍需理解、审查和验证。

## 7. 时间预算

课程持续七周，每周安排八小时。考虑毕业设计及其他安排，本项目实际计划投入约 24 小时。

| 阶段 | 预算 |
|---|---:|
| 项目、需求、设计与验收文档 | 4 小时 |
| 论文绪论初稿与资料整理 | 2 小时 |
| 员工档案、部门职位与权限 | 5 小时 |
| 请假审批 | 4 小时 |
| 网页考勤 | 3 小时 |
| 简化薪资 | 3 小时 |
| 联调、修正与交付记录 | 3 小时 |
| 合计 | 24 小时 |

以上为计划估算，实施中记录实际耗时。进度紧张时，优先压缩美化和扩展功能，保留六项必需功能及权限验证。

完整课程报告的撰写另行安排，不包含在本阶段 24 小时交付承诺中。

## 8. 交付成果与验收原则

本阶段交付：

- 项目说明、需求说明、设计说明及实施与测试计划。
- 可在本地运行的前后端代码。
- 增量数据库脚本和虚构演示数据。
- 测试记录、必要截图、运行说明及已知限制。
- 论文绪论初稿和可追溯的引用资料。

验收不仅检查功能能否正常操作，还需检查错误输入、重复请求、业务状态限制和越权访问。

金额计算、请假状态与审批规则安排针对性的自动化测试，其余功能采用明确的手动验收用例。

## 10. 范围限制

不包含多企业管理、服务器部署、真实生产运行、个税社保、银行发薪、定位打卡、硬件接入、多级审批及跨日班次。

基础版本不开发额外统计大屏或复杂导入导出功能，优先完成必需业务和学习目标。
