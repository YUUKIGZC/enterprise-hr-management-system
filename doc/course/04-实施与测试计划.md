# 企业人事管理系统实施与测试计划

## 1. 实施目标

完成六项课程必需功能，能够在本地演示主要业务流程，并理解关键实现。

以《02-需求说明》和《03-设计说明》为依据，不增加扩展功能。不以完成生产系统或毕业设计为目标。

24 小时为原始估算，不是完成保证。记录实际投入，文档阶段已经使用的时间计入预算，不重新计算。

## 2. 开发顺序

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| 1 | 员工表、基础查询与新增 | 页面能新增员工并查询，理解完整调用链 |
| 2 | 员工编辑、账号同步与部门职位保护 | 修改一致、关联校验有效 |
| 3 | 业务角色、审批配置与数据范围 | 不同账号只能访问允许的数据 |
| 4 | 请假申请与审批 | 普通员工、负责人和 HR 路径可演示 |
| 5 | 网页考勤与人工更正 | 上下班、重复限制和补录可验证 |
| 6 | 月度工资与发布 | 金额计算正确，员工只看本人已发布工资 |
| 7 | 联调与运行说明 | 从初始化到业务演示的步骤清楚可重复 |

权限随各功能实现和测试，不推迟到最后集中补充。

第一阶段先手写员工查询的一条完整链路：
页面 → 前端接口调用 → Controller → Service → Mapper → 数据库。

每次只实现一个可验证的小任务，不一次生成整个系统。

## 3. 分支与提交

- 当前文档在 docs/course-plan 分支维护，确认后通过 PR 合并到 master。
- 功能从最新 master 创建分支。
- 前后端涉及同一功能时使用相同分支名，例如 feat/employee-management。
- 每完成一个可验证的小任务进行一次提交。
- 提交前检查暂存差异，不提交真实密码、构建产物或无关修改。
- 前后端 PR 在说明中关联，记录实际执行的验证。
- 原初始化 SQL 的本地改动单独核查，不混入文档或功能提交。

## 4. 演示数据

使用虚构数据，至少准备：

- 两个部门，各一个职位。
- 一个内置超级管理员，用于账号和角色配置。
- 一个备用业务管理员账号。
- 一个 HR 账号。
- 两个部门负责人账号。
- 每个部门至少一个普通员工账号及关联档案。
- 一个未关联账号的员工档案。

默认 HR、备用管理员和各部门负责人使用不同账号。

测试账号密码仅在本地设置，不写入文档。每个角色使用独立会话测试，不能全部使用超级管理员。

## 5. 核心验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| E01 | 新增、查询、编辑员工 | 保存成功，列表与详情一致 |
| E02 | 重复工号或关联账号 | 拒绝保存 |
| E03 | 修改关联员工的部门和职位 | 档案与账号同步，失败时一起回滚 |
| E04 | 员工或负责人访问范围外档案 | 后端拒绝，不泄露受限字段 |
| E05 | 删除被人事数据引用的账号、部门或职位 | 拒绝删除，提示关联原因 |
| L01 | 普通员工、负责人、HR 申请请假 | 分别分配正确审批人 |
| L02 | 无负责人、自审或审批配置失效 | 按规则转交或拒绝 |
| L03 | 日期错误、重叠申请及并发提交 | 拒绝非法或重复申请 |
| L04 | 批准、驳回、撤回及重复处理 | 状态变化正确，终态不可再处理 |
| L05 | 非指定账号审批，或调岗后处理旧申请 | 越权被拒绝，旧分配保持 |
| A01 | 上班、下班及重复打卡 | 正常操作成功，重复或顺序错误被拒绝 |
| A02 | 并发上班请求 | 仅一条当天记录 |
| A03 | HR 补录和更正 | 原因必填，时间合法，不覆盖式补录 |
| A04 | 离职员工打卡或查看他人考勤 | 拒绝操作 |
| S01 | 5000＋200＋300－100 | 应发金额为 5400.00 |
| S02 | 负数、超精度、结果为负或超范围 | 拒绝保存 |
| S03 | 同一员工同月重复创建 | 拒绝重复工资单 |
| S04 | 工资发布后编辑及并发编辑、发布 | 已发布内容不可修改 |
| S05 | 员工查看草稿或他人工资 | 不返回数据或拒绝访问 |

越权测试必须直接调用接口验证，不能只检查按钮是否隐藏。使用浏览器开发者工具或接口工具复现请求，不把令牌复制进提交材料。

并发用例使用两个近乎同时发出的请求验证，不用单次点击代替并发测试。

## 6. 自动化测试范围

针对以下关键逻辑编写自动化测试：

- BigDecimal 金额计算、精度与范围校验。
- 请假审批人选择及自审限制。
- 请假状态转换与非法重复处理。

数据库唯一约束、事务与并发通过实际数据库测试验证，不仅使用模拟对象测试。

基础页面、表单及主要联调流程采用手动验收，避免为课程项目增加不必要的测试框架。

## 7. 测试记录

每次测试记录：

| 用例编号 | 版本或提交号 | 操作与输入 | 实际结果 | 状态 | 证据或问题 |
|---|---|---|---|---|---|
| 待填写 | 待填写 | 待填写 | 未执行 | 未测试 | 待填写 |

状态只使用“未测试”“通过”“失败”。构建成功不代表业务用例通过。

只保存关键成功页面及问题复现截图，不为每次点击制作截图。

## 8. 最终检查

- 后端执行 mvn test 和 mvn package。
- 前端执行 npm run build:prod。
- 在独立测试数据库中，按原初始化脚本和增量脚本顺序初始化，不清空现有开发数据库。
- 按运行说明启动前后端，完成六项功能演示。
- 检查各角色的数据权限及操作权限。
- 确认仓库无真实密码，许可证保留。
- 记录启动步骤、初始化顺序、环境变量、已知限制及测试结果。
- 构建或测试失败必须记录并处理，不能写成已完成验收。

## 9. 文档与论文安排

完成本计划后检查需求与设计的一致性，再确认文档基线。

论文本阶段只完成绪论初稿和引用资料整理，后续单独安排完整报告。先完成一条员工业务链路，获得实际项目理解，再集中撰写绪论；该顺序调整用于控制课程投入时间。

绪论不表述尚未完成的功能为已实现，也不将若依原有能力作为自主成果。

完整报告要求仍为正文超过 10000 字，至少 21 篇参考文献，其中英文文献 3–5 篇。
