# 企业人事管理系统需求说明

## 1. 文档目的

将项目说明中的功能范围细化为业务规则和验收条件，作为后续设计、开发和测试的依据。

本系统面向单个企业，使用虚构数据进行本地演示。未列入本文档的扩展功能不属于基础版本交付范围。

## 2. 角色与数据权限

| 角色 | 员工档案 | 部门与职位 | 工资 | 考勤 | 请假 |
|---|---|---|---|---|---|
| 员工 | 查看本人 | 不维护 | 查看本人已发布工资单 | 本人打卡、查询 | 本人提交、查询、撤回待审申请 |
| 部门负责人 | 查看直属部门基础档案及本人档案 | 不维护 | 仅查看本人已发布工资单 | 仅操作及查看本人考勤 | 查看直属部门记录，审批分配给自己的申请 |
| HR | 维护全公司档案 | 维护 | 维护和发布全公司工资单 | 查询、补录、更正全公司考勤 | 查看全公司记录，审批分配给自己的申请 |
| 系统管理员 | 全部操作 | 全部操作 | 全部操作 | 全部操作 | 全部操作，但仍禁止自审 |

部门负责人可查看的基础档案包括工号、姓名、部门、职位、入职日期和在职状态，不包含备注或登录账号信息。

角色可以组合，操作权限取各角色允许范围的并集，但禁止自审、禁止重复打卡、工资发布后只读等业务规则不能被角色权限绕过。

“管理员具有全部操作权限”不表示可以越过审批分配规则直接批准他人的申请。

所有限制由后端校验，前端同步控制入口和按钮。

## 3. 基础配置与账号关联

### 3.1 员工账号

- 一个员工档案最多关联一个登录账号，一个登录账号最多关联一个员工档案。
- HR 可以先建立未关联账号的档案；未关联账号的员工不能使用自助功能。
- 自助打卡、请假和个人查询从当前登录账号识别员工，不由客户端指定任意员工。
- 离职员工保留档案及历史记录，不能提交新请假或进行新打卡。
- 是否停用登录账号通过若依账号管理处理，不能仅依赖前端隐藏功能。

### 3.2 审批配置

管理员维护：

- 每个部门的一名负责人账号。
- 一名默认 HR 审批人。
- 一名备用管理员审批人。

审批账号必须存在、处于启用状态并具有相应业务角色。部门负责人账号还必须关联本部门在职员工。

默认 HR 和备用管理员必须是不同账号。

若依原有部门负责人姓名仅用于显示，不能作为审批身份依据。

### 3.3 基础资料维护

部门和职位复用若依现有功能及校验规则，不新增另一套部门、职位体系。

员工关联的部门和职位必须有效。已经被员工档案或业务记录引用的资料不能物理删除，可在需要时停用。

## 4. 员工信息管理

### 4.1 档案内容

| 字段 | 规则 |
|---|---|
| 工号 | 必填，去除首尾空格，全公司唯一，不区分大小写 |
| 姓名 | 必填 |
| 部门 | 必填，选择有效部门 |
| 职位 | 必填，选择有效职位 |
| 入职日期 | 必填，不能晚于当天 |
| 在职状态 | 在职、离职；新增默认在职 |
| 登录账号 | 可选，关联时检查唯一性 |
| 备注 | 可选，仅 HR 和管理员可查看及维护 |

字段长度在设计说明中与数据库及页面校验统一确定。

### 4.2 操作

- HR 和管理员可以新增、编辑、分页查询员工档案。
- 支持按工号、姓名、部门、在职状态查询。
- 基础版本不提供档案删除，离职通过修改状态记录。
- 调岗可以修改部门、职位，不改变已经提交的请假审批分配。
- 不提供员工自行修改档案的入口。

### 4.3 验收条件

- 可以新增档案，并通过查询找到。
- 重复工号或重复关联账号被拒绝，提示原因。
- 离职后历史记录仍可查询。
- 员工不能通过修改请求参数访问他人档案。
- 部门负责人不能访问其他部门员工详情或受限字段。

## 5. 薪资计算

### 5.1 业务规则

- 每名员工每个自然月最多一张工资单。
- 月份采用年、月表示；不限制为当前月份，便于演示和补录。
- 基本工资、津贴、奖金、扣款均为非负金额，精度最多两位小数。
- 输入的数值必须能精确表示为两位小数；允许规范化尾随零，例如 100.000 保存为 100.00，100.001 拒绝，不静默舍入。
- 计算公式：应发金额 = 基本工资 + 津贴 + 奖金 − 扣款。
- 应发金额不能为负数。
- 工资由后端计算，不能接受客户端自行指定的计算结果。
- 不计算个税、社保、考勤扣款或实发银行金额。

### 5.2 状态与操作

工资单状态为草稿、已发布。

- HR 和管理员可以创建和编辑草稿。
- 草稿校验通过后可以发布。
- 已发布工资单不可编辑、删除或撤回。
- 基础版本不提供工资单删除；草稿通过编辑修正。
- 员工仅能查看本人已发布工资单。
- 离职员工仍可保留历史工资单，HR 可为其补录工资。

### 5.3 验收条件

- 5000 元基本工资、200 元津贴、300 元奖金、100 元扣款，结果为 5400.00 元。
- 重复月份工资单被拒绝。
- 负数、超出精度或计算结果为负数的输入被拒绝。
- 员工看不到本人草稿及他人工资单。
- 已发布工资单的修改请求被后端拒绝。

## 6. 考勤打卡

### 6.1 时间规则

- 业务日期和打卡时间按后端 Asia/Shanghai 时区确定。
- 员工点击上班或下班按钮，后端记录当前时间。
- 每名员工每天最多一条考勤记录，包含一次上班、一次下班。
- 上班后才能下班，重复操作被拒绝。
- 不支持跨日班次；次日不能补打前一天的下班卡。
- 基础版本只记录时间，不判断迟到、早退、工作日或自动计算缺勤。

### 6.2 HR 补录与更正

- HR 和管理员可以补录或更正当天及过去日期的记录，不允许未来日期。
- 补录可以只有上班时间；如果填写下班时间，必须同时有上班时间。
- 时间属于所选日期，下班时间不能早于上班时间。
- 当天补录时间不能晚于当前后端时间。
- 每次补录、更正必须填写原因，并记录操作者及操作时间。
- 更正沿用同一天的记录，不新增重复记录。
- 不提供考勤记录删除。

### 6.3 验收条件

- 上班、下班成功后，员工可以查看当天记录。
- 未上班先下班及重复打卡被拒绝。
- 并发点击上班按钮仍只产生一条记录。
- 员工不能为他人打卡或更正记录。
- HR 不填写原因或输入错误时间时，操作被拒绝。
- 员工不能查看他人考勤。

## 7. 请假审批

### 7.1 申请内容与日期规则

- 申请内容包括类型、开始日期、结束日期和原因。
- 类型仅为事假、病假；原因必填。
- 按整天申请，开始日期不能晚于结束日期。
- 新申请开始日期不能早于当天。
- 天数为结束日期与开始日期之间的自然日数加一，包含周末和节假日。
- 同一员工待审或已批准申请不能日期重叠。
- 驳回或撤回的申请不阻止再次申请。
- 请假不自动生成考勤记录，也不自动影响工资。

### 7.2 审批人确定顺序

提交时按以下顺序确定审批人：

1. 申请人具有 HR 角色：交给备用管理员。
2. 申请人是所在部门配置的负责人：交给默认 HR。
3. 其他申请人且部门配置了负责人：交给部门负责人。
4. 部门没有配置负责人：交给备用管理员。
5. 候选审批人与申请人相同：改为备用管理员。
6. 备用管理员仍是申请人，或最终审批账号缺失、停用或不具备相应角色：阻止提交，提示完善配置。

部门已配置负责人但账号无效时，提示修正配置，不静默当作“没有负责人”。

提交时保存申请人的部门和审批人。后续调岗或修改审批配置不自动改变已有申请。

如果已有申请的审批人无法继续处理，申请人撤回待审申请，在修正配置后重新提交。基础版本不提供管理员改派功能。

### 7.3 状态与操作

状态为待审批、已批准、已驳回、已撤回。

- 提交有效申请后进入待审批状态，不提供草稿。
- 申请人可以撤回待审批申请。
- 只有被分配的审批人可以批准或驳回待审批申请。
- 驳回原因必填，批准意见可选。
- 禁止审批自己的申请。
- 已批准、已驳回、已撤回的记录不能再次审批或撤回。
- 提交后不能编辑申请内容；错误内容通过撤回并重新申请修正。
- 记录保留，不提供删除或已批准申请取消。

### 7.4 验收条件

- 普通员工、部门负责人和 HR 的申请分别进入正确审批路径。
- 无负责人时交给备用管理员。
- 缺少有效审批人或发生无法解决的自审时，提交被拒绝。
- 开始、结束日期错误或日期重叠时，提交被拒绝。
- 驳回未填写原因时，操作被拒绝。
- 申请撤回后不能被批准。
- 两次并发审批只有第一次有效状态变更成功。
- 调岗后，已有申请仍交给原审批人处理。
- 部门负责人不能审批分配给其他人的申请，即使申请来自本部门。
- HR 查看全公司申请，不等于可以审批全部申请。

## 8. 页面与操作入口

基础版本提供：

- 员工档案管理。
- 部门管理、职位管理，复用现有页面。
- 审批人配置。
- 工资管理、我的工资。
- 考勤管理、我的考勤与打卡。
- 请假记录、我的请假、待我审批。
- 我的档案。
- 账号与权限管理，复用现有页面。

页面应显示操作结果，校验失败时给出可理解的原因。列表使用分页，不要求额外统计大屏。

## 9. 非功能要求

- 前后端可以按运行说明在本地启动。
- 使用若依现有身份认证、响应格式、分页和日志能力。
- 权限与业务状态由后端校验。
- 涉及金额采用精确十进制运算。
- 重复提交与并发请求不能破坏唯一约束或业务状态。
- 真实密码不进入源码、文档或 Git 提交。
- 使用虚构数据，不展示真实个人信息。
- 不对高并发、生产可用性或服务器部署作验收承诺。

## 10. 验收与变更管理

每项功能同时验证正常操作、错误输入、权限边界和状态限制。

测试记录区分“未测试”“通过”“失败”，不得将编译成功等同于业务验收通过。

需求变更先更新本文档，说明变更原因和对设计、代码及测试的影响，再实施修改。
