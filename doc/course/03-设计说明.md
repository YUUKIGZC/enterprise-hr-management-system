# 企业人事管理系统设计说明

## 1. 设计目标

在若依现有架构上增加人事业务，复用登录账号、角色、部门、岗位和权限机制。

本设计以《02-需求说明》为依据。先确定数据关系，再细化字段、接口、页面和权限实现。本文当前为设计草稿，尚未执行数据库变更。

## 2. 数据关系

### 2.1 复用的数据

| 原有表 | 用途 |
|---|---|
| sys_user | 登录账号 |
| sys_role、sys_user_role | 角色及账号与角色的关联 |
| sys_dept | 部门 |
| sys_post | 岗位，对应课程中的职位 |

登录账号与员工档案分开：账号用于身份认证和授权，档案用于记录员工业务信息。系统管理员账号可以不关联员工档案，但使用员工自助功能必须有关联档案。

### 2.2 新增业务表

| 表名 | 用途 | 主要关系与约束 |
|---|---|---|
| hr_employee | 员工档案 | 工号唯一；登录账号可为空，非空时唯一；每名员工关联一个部门、一个职位 |
| hr_dept_approver | 部门负责人配置 | 每个部门最多一条配置，关联负责人账号 |
| hr_approval_config | 全局审批配置 | 固定一条配置，关联默认 HR 和备用管理员账号 |
| hr_salary | 月度工资单 | 关联员工；员工与月份组合唯一 |
| hr_attendance | 每日考勤 | 关联员工；员工与考勤日期组合唯一 |
| hr_leave | 请假申请 | 关联员工，保存提交时部门和审批人 |

部门负责人配置和全局审批配置分开，避免在每个部门重复保存默认 HR 与备用管理员。

### 2.3 关联方式

员工档案保存：

- user_id：关联登录账号，可以为空。
- dept_id：关联部门，必填。
- post_id：关联职位，必填。

工资、考勤和请假均通过 employee_id 关联员工档案。

请假另外保存：

- dept_id：申请提交时的部门。
- approver_user_id：申请提交时确定的审批账号。

员工调岗时只更新当前档案归属，不修改已提交申请保存的部门和审批人。

### 2.4 部门与职位的一致性

员工档案是人事业务中部门、职位归属的依据。

员工关联账号后，维护员工部门和职位时，同时同步若依账号的部门与岗位关联，在同一事务中完成。基础版本每名员工只有一个职位。

对于已关联员工档案的账号，若依账号管理中涉及部门、岗位的修改必须与档案保持一致，不能产生两套不同归属；具体入口校验在权限与接口设计中展开。

### 2.5 历史记录保留

员工离职通过状态记录，不删除档案。

工资单、考勤和请假保留历史记录。已被业务数据引用的账号、部门和职位不能物理删除，必要时停用。

本阶段不建立完整的调岗历史表。请假保留提交时部门和审批人；工资、考勤列表中展示的员工姓名、部门和职位默认来自当前档案，不宣称为历史组织快照。

## 3. 数据关系示意

    登录账号 0..1 ←→ 0..1 员工档案
                            │
                            ├── 属于一个部门
                            ├── 对应一个职位
                            ├── 多张月度工资单
                            ├── 多条每日考勤记录
                            └── 多条请假申请
                                      │
                                      ├── 提交时部门
                                      └── 指定审批账号

    部门 → 最多一条负责人配置 → 负责人账号
    全局审批配置 → 默认 HR 账号、备用管理员账号

## 4. 员工档案表设计

### 4.1 表名与用途

表名：hr_employee。

用途：保存员工当前档案，与若依登录账号、部门和职位建立关联。离职保留档案，不提供物理删除接口。

### 4.2 字段定义

| 字段 | MySQL 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| employee_id | BIGINT | 是 | 自增 | 主键，内部员工编号 |
| employee_no | VARCHAR(32) | 是 | 无 | 工号，去除首尾空格，不区分大小写 |
| employee_name | VARCHAR(50) | 是 | 无 | 姓名，去除首尾空格 |
| user_id | BIGINT | 否 | NULL | 关联 sys_user.user_id |
| dept_id | BIGINT | 是 | 无 | 关联 sys_dept.dept_id |
| post_id | BIGINT | 是 | 无 | 关联 sys_post.post_id |
| hire_date | DATE | 是 | 无 | 入职日期，不能晚于业务当天 |
| employment_status | CHAR(1) | 是 | 0 | 0：在职；1：离职 |
| remark | VARCHAR(500) | 否 | NULL | 备注，仅 HR 和管理员可访问 |
| create_by | VARCHAR(64) | 是 | 空字符串 | 创建账号名称 |
| create_time | DATETIME | 是 | 无 | 创建时间 |
| update_by | VARCHAR(64) | 否 | NULL | 最后修改账号名称 |
| update_time | DATETIME | 否 | NULL | 最后修改时间 |

业务日期和时间统一按 Asia/Shanghai 时区处理。

Java 中，编号使用 Long，状态使用 String，日期和审计时间沿用项目现有日期处理方式。创建人、修改人及时间由后端填写，不允许客户端指定。

### 4.3 约束与索引

| 名称 | 类型 | 字段 | 作用 |
|---|---|---|---|
| PRIMARY | 主键 | employee_id | 唯一识别记录 |
| uk_hr_employee_no | 唯一索引 | employee_no | 防止重复工号 |
| uk_hr_employee_user | 唯一索引 | user_id | 防止同一账号关联多个员工 |
| idx_hr_employee_dept | 普通索引 | dept_id | 支持部门筛选及关联检查 |
| idx_hr_employee_post | 普通索引 | post_id | 支持职位关联及删除检查 |

使用 InnoDB 和 utf8mb4 字符集。employee_no 列显式采用 utf8mb4_0900_ai_ci 排序规则，使数据库唯一约束不区分大小写。

MySQL 唯一索引允许多个 NULL，因此多个未关联账号的员工档案可以同时存在。

姓名包含查询不额外建立普通索引；普通 B-tree 索引通常不能加速前后通配符查询。

### 4.4 关联完整性

新增员工表对 sys_user、sys_dept、sys_post 设置外键，删除和更新采用 RESTRICT，不级联删除员工档案。

后端仍需检查关联对象是否存在、是否启用及是否满足业务角色规则。外键只能保证记录存在，不能保证账号启用或部门状态正确。

数据库约束是最终保障，业务层提前校验并返回可理解的错误信息。

### 4.5 员工与账号的归属同步

员工未关联账号时，仅维护员工档案。

关联账号或修改已关联员工的部门、职位时，在同一事务内：

1. 保存员工档案。
2. 将账号的 dept_id 同步为员工部门。
3. 更新该账号的 sys_user_post 关联，使其只有员工当前职位。

只同步部门和职位，不自动改变账号角色、密码或启用状态。

若依账号编辑入口对已关联员工的账号禁止单独改变部门和岗位，提示通过员工档案管理修改。停用账号及管理角色仍沿用原有权限。

解除账号关联不删除账号，也不清除该账号已有部门和岗位；关联新账号时按员工当前归属同步。账户关联变更不迁移历史请假的审批人。

### 4.6 输入与业务校验

- 工号和姓名去除首尾空格后不能为空。
- 字符长度不能超过字段限制。
- 工号新增或修改时检查全公司唯一，编辑时排除当前员工。
- user_id 为空表示未关联；非空时检查账号存在、启用且未关联其他员工。
- 部门和职位必须存在且启用。
- hire_date 必填，不能晚于当前业务日期。
- employment_status 只接受 0 或 1。
- remark 最多 500 个字符。
- 新增默认在职；编辑允许修改为离职，不自动停用登录账号。
- 已被配置为部门负责人的员工，不允许调离该部门、离职或解除、更换账号；先调整负责人配置，再修改档案。

离职员工仍可被查询及维护，不允许提交新请假或进行新打卡。

### 4.7 并发与错误处理

前端检查和业务层查询不能代替唯一约束。

两个请求同时使用相同工号或账号时，由数据库唯一约束阻止重复；后端将对应冲突转为明确提示，不向页面暴露数据库异常详情。

档案保存与账号归属同步必须一起成功或一起回滚。

## 5. 审批配置表设计

### 5.1 部门负责人配置

表名：hr_dept_approver。

每个部门最多配置一名负责人。配置关联登录账号，不使用姓名判断审批身份。

| 字段 | MySQL 类型 | 必填 | 说明 |
|---|---|---|---|
| dept_id | BIGINT | 是 | 主键，关联 sys_dept.dept_id |
| approver_user_id | BIGINT | 是 | 负责人账号，关联 sys_user.user_id |
| create_by | VARCHAR(64) | 是 | 创建账号名称 |
| create_time | DATETIME | 是 | 创建时间 |
| update_by | VARCHAR(64) | 否 | 最后修改账号名称 |
| update_time | DATETIME | 否 | 最后修改时间 |

dept_id 作为主键，直接保证一个部门最多一条配置。approver_user_id 建立普通索引，用于查询负责人负责的部门及检查账号引用。

两个关联字段设置外键，采用 RESTRICT，不级联删除。

保存配置时检查：

- 部门存在且启用。
- 账号存在且启用，具有部门负责人角色。
- 账号关联在职员工，员工属于该部门。

允许管理员新增、修改及移除配置。移除表示该部门没有负责人，新申请按备用管理员规则处理，已经提交的申请不改变审批人。

配置的移除和重新创建分别记录操作日志；审计字段由后端填写。

### 5.2 全局审批配置

表名：hr_approval_config。

固定一条记录，config_id 为 1，保存全公司共用的默认 HR 和备用管理员。

| 字段 | MySQL 类型 | 必填 | 说明 |
|---|---|---|---|
| config_id | BIGINT | 是 | 主键，固定为 1 |
| default_hr_user_id | BIGINT | 是 | 默认 HR 账号，关联 sys_user.user_id |
| fallback_admin_user_id | BIGINT | 是 | 备用管理员账号，关联 sys_user.user_id |
| create_by | VARCHAR(64) | 是 | 创建账号名称 |
| create_time | DATETIME | 是 | 创建时间 |
| update_by | VARCHAR(64) | 否 | 最后修改账号名称 |
| update_time | DATETIME | 否 | 最后修改时间 |

数据库设置以下约束：

- config_id 必须为 1。
- default_hr_user_id 与 fallback_admin_user_id 不得相同。
- 两个账号字段设置外键，采用 RESTRICT。

初始化时不预填任意账号。管理员第一次保存有效配置时创建记录，之后更新该记录，不提供删除接口。

保存配置时检查：

- 默认 HR 账号启用且具有 HR 角色。
- 备用管理员账号启用且具有管理员身份。
- 两个账号不同。

管理员身份包括若依内置超级管理员，以及本项目明确配置的业务管理员角色，不以用户名判断。

### 5.3 配置权限与有效性

审批配置仅允许管理员维护。

账号启用状态及角色可能在配置保存后变化，因此申请提交时重新检查实际候选审批人的有效性。

部门已配置负责人但配置无效时，阻止申请提交并提示修正配置；不静默转交备用管理员。

部门未配置负责人时，使用备用管理员。发生自审时，同样使用备用管理员；备用管理员仍为申请人或不可用时，阻止提交。

基础版本不阻止管理员停用审批账号或调整其角色，但需提示其可能影响审批。已提交申请没有自动改派机制，应修正账号配置，或由申请人撤回后重新申请。

审批操作时再次检查：

- 当前账号启用并具备相应审批角色。
- 当前账号等于申请保存的审批账号。
- 当前账号不是申请人。
- 申请仍处于待审批状态。

部门负责人资格以当前账号仍出现在有效部门负责人配置中为准。已有申请的审批分配不因申请人调岗而改变。

### 5.4 示例

销售部配置负责人账号 A，默认 HR 为 B，备用管理员为 C：

| 申请人情况 | 审批人 |
|---|---|
| 销售部普通员工 | A |
| 销售部负责人 A | B |
| HR B | C |
| 未配置负责人的部门员工 | C |
| 最终候选审批人也是申请人 | 转给 C；如果 C 仍是申请人，拒绝提交 |

多个业务角色同时存在时，先判断 HR，再判断是否为所在部门负责人，最后采用普通员工路径。

## 6. 月度工资表设计

### 6.1 表名与用途

表名：hr_salary。

保存员工每个自然月的工资组成、计算结果和发布状态。每名员工每月最多一张工资单，允许为离职员工补录工资。

### 6.2 字段定义

| 字段 | MySQL 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| salary_id | BIGINT | 是 | 自增 | 主键 |
| employee_id | BIGINT | 是 | 无 | 关联 hr_employee.employee_id |
| salary_month | DATE | 是 | 无 | 工资月份，统一保存为当月第一天 |
| base_salary | DECIMAL(12,2) | 是 | 0.00 | 基本工资 |
| allowance | DECIMAL(12,2) | 是 | 0.00 | 津贴 |
| bonus | DECIMAL(12,2) | 是 | 0.00 | 奖金 |
| deduction | DECIMAL(12,2) | 是 | 0.00 | 扣款 |
| payable_amount | DECIMAL(12,2) | 是 | 无 | 后端计算的应发金额 |
| status | CHAR(1) | 是 | 0 | 0：草稿；1：已发布 |
| published_by | VARCHAR(64) | 否 | NULL | 发布账号名称 |
| published_time | DATETIME | 否 | NULL | 发布时间 |
| create_by | VARCHAR(64) | 是 | 空字符串 | 创建账号名称 |
| create_time | DATETIME | 是 | 无 | 创建时间 |
| update_by | VARCHAR(64) | 否 | NULL | 最后修改账号名称 |
| update_time | DATETIME | 否 | NULL | 最后修改时间 |

salary_month 示例：2026 年 10 月保存为 2026-10-01。前端显示和输入采用 YYYY-MM，后端统一转换，不接受任意日作为月份。

基础版本不保存银行卡、个税或社保信息。

### 6.3 约束与索引

- salary_id 为主键。
- employee_id 与 salary_month 建立组合唯一索引，防止同一员工同月重复工资单。
- salary_month 建立普通索引，支持按月份查询全公司工资。
- employee_id 设置外键，采用 RESTRICT，禁止级联删除。
- 数据库 CHECK 约束保证月份日期为每月第一天、状态合法、各金额非负。
- CHECK 约束保证 payable_amount 等于各项金额计算结果。

组合唯一索引同时支持按 employee_id 查询，不再单独建立员工索引。

### 6.4 金额计算与校验

公式：

payable_amount = base_salary + allowance + bonus − deduction

四项输入金额必填，页面默认填 0.00。后端拒绝缺失值，不依赖数据库默认值掩盖遗漏。

单项输入和计算结果范围均为 0.00 至 9,999,999,999.99。

后端使用 BigDecimal 计算，不使用 float 或 double，不通过二进制浮点数构造金额。

输入最多两位小数。数学值可精确表示为两位小数的尾随零允许规范化，例如 100.000 可保存为 100.00；100.001 必须拒绝，不进行静默舍入。

计算结果必须非负且不超出字段范围，统一保存为两位小数。

客户端不提交 payable_amount，后端每次创建或编辑草稿时重新计算。即使客户端传入该字段，也不能据此修改计算结果。

### 6.5 创建与编辑

只有 HR 和管理员可以创建、编辑工资草稿。

- 创建时员工、月份和工资组成通过校验，状态固定为草稿。
- employee_id、salary_month 在创建后不可修改，避免工资单被转移到其他员工或月份。
- 编辑只允许修改四项金额。
- 不提供工资单删除接口。
- 不限制月份必须是当前月份，允许历史补录和未来月份草稿。

每次修改记录操作者和时间。

### 6.6 发布

工资单状态只允许：

草稿 → 已发布

发布时校验金额及计算结果，保存发布人和发布时间。

已发布后不能编辑、删除、撤回或再次发布。基础版本不提供已发布工资单更正功能，发布前应核对内容。

发布与编辑使用数据库行锁，在同一事务中读取并检查状态后执行操作，防止发布与修改并发导致已发布内容被覆盖。

### 6.7 查询与权限

HR 和管理员可以分页查询全公司工资单，按员工、月份和发布状态筛选。

员工通过当前登录账号关联的员工档案，查询本人已发布工资单。部门负责人没有额外的部门工资查询权限。

列表和详情都必须执行同样的数据权限检查，不能仅限制列表入口。

离职员工的历史工资保留；其能否登录由账号启用状态决定。

### 6.8 验收示例

| 输入或操作 | 预期结果 |
|---|---|
| 基本工资 5000、津贴 200、奖金 300、扣款 100 | 应发金额 5400.00 |
| 输入负数或 100.001 | 拒绝保存 |
| 扣款超过其他三项合计 | 拒绝保存 |
| 金额计算结果超过字段范围 | 拒绝保存 |
| 同一员工同月再次创建工资单 | 拒绝创建 |
| 编辑已发布工资单 | 拒绝修改 |
| 员工查询本人草稿或他人工资单 | 不返回数据，详情请求拒绝访问 |
| 发布与编辑同时发生 | 按事务先后处理，发布后不再允许编辑 |

## 7. 每日考勤表设计

### 7.1 表名与用途

表名：hr_attendance。

记录员工每日的上班、下班时间，以及最近一次人工补录或更正的信息。

业务日期和时间统一按后端 Asia/Shanghai 时区处理，不使用浏览器提供的时间作为员工打卡时间。

### 7.2 字段定义

| 字段 | MySQL 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| attendance_id | BIGINT | 是 | 自增 | 主键 |
| employee_id | BIGINT | 是 | 无 | 关联 hr_employee.employee_id |
| attendance_date | DATE | 是 | 无 | 考勤所属日期 |
| clock_in_time | DATETIME | 是 | 无 | 上班时间 |
| clock_out_time | DATETIME | 否 | NULL | 下班时间，未下班时为空 |
| corrected_by | VARCHAR(64) | 否 | NULL | 最近一次人工补录或更正账号 |
| corrected_time | DATETIME | 否 | NULL | 最近一次人工补录或更正时间 |
| correction_reason | VARCHAR(500) | 否 | NULL | 最近一次人工补录或更正原因 |
| create_by | VARCHAR(64) | 是 | 空字符串 | 创建账号名称 |
| create_time | DATETIME | 是 | 无 | 创建时间 |
| update_by | VARCHAR(64) | 否 | NULL | 最后修改账号名称 |
| update_time | DATETIME | 否 | NULL | 最后修改时间 |

不另外保存“已上班”“已下班”状态，避免状态与时间字段不一致：

- 当天没有记录：未打卡。
- 有上班时间、无下班时间：已上班。
- 两个时间均有值：已下班。

表中保存最近一次更正信息；各次人工操作及原因通过若依操作日志记录，不在本版本建立独立历史表。

### 7.3 约束与索引

- attendance_id 为主键。
- employee_id 与 attendance_date 建立组合唯一索引。
- attendance_date 建立普通索引，支持全公司按日期查询。
- employee_id 设置外键，采用 RESTRICT，不级联删除。
- CHECK 约束保证上班时间属于 attendance_date。
- 下班时间非空时，CHECK 约束保证其属于同一天且不早于上班时间。

组合唯一索引同时支持员工考勤查询，不再单独建立员工索引。

不能晚于当前时间、员工是否在职等动态规则，由业务层检查。

### 7.4 员工打卡

员工打卡接口不接受 employee_id、考勤日期或打卡时间，由后端根据当前登录账号和当前时间确定。

上班流程：

1. 识别账号关联的员工，检查员工在职。
2. 获取当前业务日期和时间。
3. 检查当天记录是否存在。
4. 不存在则创建记录，保存上班时间。
5. 已存在则拒绝，提示当天已经上班打卡。

下班流程：

1. 识别账号关联的在职员工。
2. 获取当前业务日期和时间。
3. 检查当天记录是否存在。
4. 不存在则提示先上班打卡。
5. 已有下班时间则拒绝重复操作。
6. 当前时间不早于上班时间时，保存下班时间。

不查询前一天记录补打下班卡，不支持跨日班次。

HR 已补录当天上班时间、且没有下班时间时，员工可以正常下班打卡；已有时间不能通过员工打卡接口覆盖。

### 7.5 HR 补录与更正

HR 和管理员可以为已有员工补录或更正今天及过去日期的考勤，包括离职员工的历史记录。

每次提交必须包含：

- 员工。
- 考勤日期。
- 上班时间。
- 可选的下班时间。
- 非空的补录或更正原因，最多 500 个字符。

校验规则：

- 考勤日期不能晚于当天。
- 上班、下班时间必须属于该日期。
- 下班时间不能早于上班时间。
- 今天的时间不能晚于当前后端时间。
- 同一天已有记录时进行更正，不创建第二条记录。

更正允许将下班时间清空，以修正错误下班记录；上班时间不能为空。

已存在记录的 employee_id 和 attendance_date 不可修改。错误归属不通过修改编号或日期转移，基础版本也不提供删除接口。

补录和更正保存操作人、操作时间及原因，并记录操作日志。员工自行下班时，不清除已有人工更正信息。

### 7.6 事务与并发

上班、下班和人工补录、更正采用统一锁顺序：

1. 在事务中锁定目标员工档案行。
2. 检查员工状态及关联情况。
3. 读取并处理目标日期考勤记录。
4. 提交事务。

锁定员工行可以协调当天考勤尚不存在时的并发操作，避免仅锁定考勤记录无法覆盖首次创建的情况。

员工状态和账号关联修改同样应遵守员工行锁约定。数据库组合唯一约束作为重复记录的最终保障。

所有校验失败不写入部分结果。数据库冲突转换为业务提示，不暴露 SQL 或堆栈详情。

### 7.7 查询权限

- 员工和部门负责人只能查询本人考勤。
- HR 和管理员可以查询全公司考勤。
- 支持按员工、起止日期分页查询。
- 详情接口执行与列表一致的数据范围检查。
- 不提供迟到、早退、缺勤判断，也不根据请假自动生成记录。

### 7.8 验收示例

| 操作 | 预期结果 |
|---|---|
| 在职员工首次上班打卡 | 创建当天记录 |
| 同一天再次上班打卡 | 拒绝重复打卡 |
| 没有当天上班记录时下班 | 提示先上班打卡 |
| 同一天再次下班打卡 | 拒绝重复打卡 |
| 两个并发上班请求 | 仅一个成功，只有一条记录 |
| 离职员工打卡 | 拒绝操作 |
| HR 补录过去日期并填写原因 | 保存成功 |
| 下班早于上班或时间跨日 | 拒绝保存 |
| 补录未来日期或今天的未来时间 | 拒绝保存 |
| 员工访问他人考勤 | 拒绝访问 |
| 员工下班与 HR 更正并发 | 串行处理，每次操作均重新校验 |

## 8. 请假申请表设计

### 8.1 表名与用途

表名：hr_leave。

保存员工请假申请、提交时部门、指定审批账号及处理结果。提交后不允许修改申请内容，不提供删除接口。

### 8.2 字段定义

| 字段 | MySQL 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| leave_id | BIGINT | 是 | 自增 | 主键 |
| employee_id | BIGINT | 是 | 无 | 申请员工，关联 hr_employee |
| applicant_user_id | BIGINT | 是 | 无 | 提交时申请账号，关联 sys_user |
| dept_id | BIGINT | 是 | 无 | 提交时部门，关联 sys_dept |
| approver_user_id | BIGINT | 是 | 无 | 提交时确定的审批账号，关联 sys_user |
| approver_type | CHAR(1) | 是 | 无 | 0：部门负责人；1：HR；2：管理员 |
| leave_type | CHAR(1) | 是 | 无 | 0：事假；1：病假 |
| start_date | DATE | 是 | 无 | 开始日期 |
| end_date | DATE | 是 | 无 | 结束日期 |
| leave_days | INT | 是 | 无 | 后端计算的自然日天数 |
| reason | VARCHAR(500) | 是 | 无 | 请假原因 |
| status | CHAR(1) | 是 | 0 | 0：待审批；1：已批准；2：已驳回；3：已撤回 |
| approval_comment | VARCHAR(500) | 否 | NULL | 审批意见；驳回时必填 |
| approved_time | DATETIME | 否 | NULL | 审批完成时间 |
| withdrawn_time | DATETIME | 否 | NULL | 撤回时间 |
| create_by | VARCHAR(64) | 是 | 空字符串 | 提交账号名称 |
| create_time | DATETIME | 是 | 无 | 提交时间 |
| update_by | VARCHAR(64) | 否 | NULL | 最后处理账号名称 |
| update_time | DATETIME | 否 | NULL | 最后处理时间 |

approved_time 表示批准或驳回的处理时间，不单指批准。

申请账号、部门、审批账号和审批身份在提交时保存，不因档案调岗、账号关联或默认审批配置改变而自动更新。

### 8.3 约束与索引

- leave_id 为主键。
- employee_id、status、start_date 建立组合索引，支持本人查询和日期重叠检查。
- approver_user_id、status、create_time 建立组合索引，支持待我审批。
- dept_id、create_time 建立组合索引，支持部门记录查询。
- create_time 建立普通索引，支持全公司按提交时间查询。
- employee_id、applicant_user_id、dept_id、approver_user_id 设置外键，采用 RESTRICT。

CHECK 约束保证：

- 请假类型、审批身份和状态取值合法。
- end_date 不早于 start_date。
- leave_days 等于日期差加一。
- approver_user_id 不等于 applicant_user_id。
- 待审批时审批和撤回时间为空。
- 已批准、已驳回时审批时间非空，撤回时间为空。
- 已撤回时撤回时间非空，审批时间为空。
- 已驳回时审批意见去除首尾空格后非空。

跨记录的日期重叠不能用普通 CHECK 约束保证，由事务中的业务查询检查。

### 8.4 申请提交

提交接口仅接受请假类型、开始日期、结束日期和原因。

员工编号、申请账号、部门、审批人、天数及状态全部由后端确定，不采用客户端传入值。

处理流程：

1. 根据当前登录账号找到员工档案，并锁定员工行。
2. 检查账号关联有效且员工在职。
3. 校验类型、日期和原因。
4. 确定并校验审批人，保存实际采用的审批身份。
5. 检查同一员工是否存在重叠的待审批或已批准申请。
6. 计算自然日天数并创建待审批记录。
7. 提交事务。

开始日期不能早于当前业务日期，原因去除首尾空格后必填，最多 500 个字符。

日期重叠判断采用：

已有申请开始日期 ≤ 新申请结束日期，
且已有申请结束日期 ≥ 新申请开始日期。

例如，已有申请为 10 月 12 日至 14 日，新申请从 14 日开始仍属于重叠；从 15 日开始不重叠。

提交时锁定员工行，使同一员工的并发申请按顺序检查，避免两个请求同时通过重叠检查。

### 8.5 审批人选择

按以下顺序处理：

1. 申请账号具有 HR 角色：选择备用管理员。
2. 申请账号是所在部门配置的负责人：选择默认 HR。
3. 普通员工且部门配置了负责人：选择部门负责人。
4. 部门没有配置负责人：选择备用管理员。
5. 候选审批人是申请人：改选备用管理员。
6. 最终候选仍是申请人，或账号缺失、停用、身份无效：拒绝提交。

已配置部门负责人但账号无效时，拒绝提交并提示修正配置，不转交备用管理员。

只要求当前审批路径涉及的配置有效；普通员工走部门负责人路径时，不要求先设置全局审批配置。

审批身份按实际选择结果保存，不能由客户端指定，也不因审批账号同时具有多个角色而任意变化。

### 8.6 状态变化

| 当前状态 | 操作 | 目标状态 | 条件 |
|---|---|---|---|
| 无记录 | 提交 | 待审批 | 输入、员工、审批配置和日期重叠检查通过 |
| 待审批 | 批准 | 已批准 | 指定审批人操作，身份有效且不是申请人 |
| 待审批 | 驳回 | 已驳回 | 同上，并填写驳回原因 |
| 待审批 | 撤回 | 已撤回 | 原申请账号操作，仍关联该员工 |
| 已批准、已驳回、已撤回 | 再次审批或撤回 | 不变 | 拒绝操作 |

不提供草稿、申请编辑、已批准申请取消和管理员改派。

离职员工不能提交新申请，但账号仍启用且关联未变时，可以撤回原有待审批申请。

### 8.7 审批权限

审批时必须同时满足：

- 当前登录账号等于 approver_user_id。
- 当前登录账号不等于 applicant_user_id。
- 当前账号没有关联该申请的员工档案，避免更换账号后审批自己的申请。
- 申请处于待审批状态。
- 当前账号具备保存的审批身份。

身份有效性：

- 部门负责人：仍具有负责人角色，并在有效负责人配置中被指定；所负责部门不要求与申请员工当前部门相同。
- HR：仍具有 HR 角色。
- 管理员：仍具有管理员身份。

已经提交的申请由指定账号处理。更换默认 HR 或备用管理员不会自动撤销原审批人的分配，但原账号必须仍具有相应身份。

账号失效时不自动改派，可恢复有效配置，或由申请人撤回后重新提交。

### 8.8 查询权限

- 员工查看本人申请，依据当前关联的 employee_id 查询。
- 原提交账号解除关联后，不因曾经提交过申请而继续获得员工自助查询权限。
- 部门负责人查看提交时 dept_id 属于其当前负责部门的申请。
- 指定审批人可以在“待我审批”中查看分配给自己的待审批申请。
- 指定审批人可以查看分配给自己的申请详情及处理结果，不因负责人配置变化失去该记录的查看权；审批操作仍需检查当前身份、指定账号及待审批状态。
- HR 和管理员可以查询全公司申请，但不能绕过审批分配和禁止自审规则。

支持按员工、类型、状态、提交时部门及请假日期范围分页查询。员工和负责人能使用的筛选范围由后端限制。

### 8.9 并发处理

审批与撤回在事务中锁定申请行，读取最新状态后再校验并更新。

两个审批请求，或审批与撤回同时发生时，仅第一次有效处理成功，后续请求读取终态后被拒绝。

提交采用员工行锁；审批和撤回只锁申请行，不再反向锁员工行，避免形成员工行与申请行之间的相反锁顺序。

数据库操作失败时整个事务回滚，不留下部分审批结果。

### 8.10 验收示例

| 场景 | 预期结果 |
|---|---|
| 普通员工申请 | 分配本部门负责人 |
| 部门负责人申请 | 分配默认 HR |
| HR 申请 | 分配备用管理员 |
| 无负责人部门的员工申请 | 分配备用管理员 |
| 最终审批人仍为申请人 | 拒绝提交 |
| 同一员工并发提交重叠日期 | 最多一条申请成功 |
| 原申请已经撤回或驳回 | 允许重新申请相同日期 |
| 非指定审批人批准申请 | 拒绝操作 |
| 驳回时不填写原因 | 拒绝操作 |
| 申请人调岗 | 原申请部门和审批人不变 |
| 批准与撤回同时发生 | 仅一次状态变化成功 |
| 更换账号后尝试审批本人员工档案的申请 | 拒绝操作 |

## 9. 接口通用约定

### 9.1 路径与响应

新增业务接口统一使用 /hr 前缀。

沿用若依现有响应格式：

- 分页列表返回 TableDataInfo，包含 rows、total、code、msg。
- 详情及操作结果返回 AjaxResult。
- 分页参数使用 pageNum、pageSize，沿用项目的分页限制。
- 日期格式为 YYYY-MM-DD。
- 日期时间格式为 YYYY-MM-DD HH:mm:ss，按 Asia/Shanghai 解释。
- 工资月份格式为 YYYY-MM。
- 金额在业务接口中使用十进制字符串，例如 "5400.00"，避免前端浮点运算改变金额。

前端显示后端计算结果，不承担最终金额计算、身份识别或审批人选择。

### 9.2 请求与实体分离

请求对象仅包含本操作允许修改的字段，不直接使用数据库实体接收所有请求。

例如，员工新增请求不包含：

- employeeId。
- createBy、createTime。
- updateBy、updateTime。

工资请求不包含计算结果、发布状态或发布人。请假请求不包含员工身份、审批人和状态。

权限和系统生成字段即使被客户端额外传入，也不能影响保存结果。

### 9.3 业务角色

新增业务角色使用固定 role_key：

| 角色 | role_key |
|---|---|
| 业务管理员 | hr_admin |
| HR | hr_hr |
| 部门负责人 | hr_leader |
| 员工 | hr_employee |

若依内置超级管理员按现有超级管理员判断方式识别；其他管理员通过 hr_admin 角色识别，不依赖用户名、角色名称或随意指定的角色编号。

员工自助入口允许上述四类角色使用，但必须关联员工档案，并遵守在职状态等业务规则。

菜单和按钮权限控制操作入口；业务角色和数据范围校验控制实际业务访问。两者都必须通过。

### 9.4 权限实现原则

后端执行两层检查：

1. 接口检查操作权限标识。
2. Service 检查业务角色、记录归属和业务状态。

管理员与 HR 查询全公司员工。负责人查询当前有效配置下直属部门员工，并可查看本人档案。其他员工只能通过本人接口查看本人档案。

负责人管理范围从 hr_dept_approver 查询，不能仅根据账号当前 dept_id 推断，也不自动包含下级部门。

数据范围条件在分页查询之前加入 SQL，不能先查询全部记录再在 Java 或前端过滤。

详情接口单独检查范围，不能认为用户能打开列表就可以查看任意 ID。

### 9.5 错误处理

沿用若依现有认证、权限异常及业务异常处理机制。

区分：

- 登录失效。
- 操作权限不足。
- 输入不合法。
- 重复数据。
- 业务状态不允许。
- 配置缺失或失效。

对于不在可访问范围内的记录，统一提示“记录不存在或无权访问”，不暴露他人数据是否存在。

不向页面返回 SQL、密码或内部堆栈。

### 10.1 接口清单

| 方法 | 路径 | 用途 | 操作权限 |

| GET | /hr/employee/list | 分页查询员工档案 | hr:employee:list |

新增和编辑仅允许 HR、管理员操作。普通员工只授予本人查询权限，不授予通用员工列表、详情权限。

负责人可以访问列表和详情，但 Service 必须限制部门范围，并隐藏受限字段。

### 10.2 列表请求

支持以下参数：

| 参数 | 用途 |

| pageSize | 每页条数 |
| employeeNo | 工号包含查询 |
| employeeName | 姓名包含查询 |
| deptId | 部门筛选 |
| employmentStatus | 在职状态筛选 |

负责人传入其他部门编号时，不扩大范围；查询同时应用允许访问的部门条件，结果为空。

列表固定按 employee_id 降序排列，基础版本不接收客户端自定义排序表达式。

列表返回：

- employeeId。
- employeeNo。
- employeeName。
- deptId、deptName。
- postId、postName。
- hireDate。
- employmentStatus。

列表不返回登录账号、备注和审计字段。

### 10.3 新增与编辑请求

请求字段：

| 参数 | 必填 | 说明 |
|---|---|---|
| employeeNo | 是 | 工号 |
| employeeName | 是 | 姓名 |
| deptId | 是 | 部门编号 |
| postId | 是 | 职位编号 |
| hireDate | 是 | 入职日期 |
| employmentStatus | 编辑时必填 | 新增固定为在职 |
| userId | 否 | 关联账号编号，NULL 表示未关联 |
| remark | 否 | 备注 |

编辑采用完整表单提交，不是局部更新。编辑时 userId 为 NULL 表示解除关联，remark 为 NULL 表示清空备注。

员工编号只从路径取得，不允许通过请求正文改变目标记录。

新增成功返回新 employeeId；编辑成功返回操作成功提示。前端重新查询以获取最新信息。

### 10.4 详情返回

HR 和管理员可以查看全部员工业务字段，以及创建和修改信息。

部门负责人查看其他员工时，仅返回第 2 节约定的基础档案字段，不返回 userId、账号信息、remark 或审计信息。

本人接口返回本人基础档案，不返回备注、账号关联配置和审计字段。

使用独立响应对象控制字段，不能仅在页面上隐藏受限字段。

### 10.5 关联选项

员工编辑页使用专用候选查询接口，复用现有部门、岗位和账号数据，不依赖额外的系统管理权限。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /hr/employee/options/depts | 查询启用部门 |
| GET | /hr/employee/options/posts | 查询启用职位 |
| GET | /hr/employee/options/users | 分页查询可关联账号 |

三个接口均要求 hr:employee:options 权限，并且只允许 HR 和管理员访问。

部门、职位返回 id、name。

账号查询接受 keyword、pageNum、pageSize，以及可选 employeeId。keyword 按账号名称或昵称搜索，返回 userId、userName、nickName、status。

账号候选仅包含启用且未关联员工的账号；编辑时额外保留当前员工已关联账号，即使其已停用，也显示状态以便修正。

employeeId 必须经后端校验，不能用于任意扩大查询范围。

候选查询只辅助选择。保存时重新检查对象状态、账号唯一性和关联规则，停用账号不能作为有效关联保存。

### 10.6 保存事务

新增及编辑事务包括：

1. 校验操作权限和请求。
2. 编辑时锁定员工行。
3. 校验员工归属、负责人配置限制及关联对象。
4. 保存员工档案。
5. 必要时同步账号部门和唯一岗位关联。
6. 提交事务。

关联账号变更涉及账号唯一性和账号数据同步，锁顺序及若依账号编辑入口的保护措施，在跨模块事务设计中统一确定。

任何步骤失败，档案与账号同步一起回滚。

## 12. 工资接口

### 12.1 接口清单

| 方法 | 路径 | 用途 | 操作权限 |
|---|---|---|---|
| GET | /hr/salary/list | 分页查询全公司工资单 | hr:salary:list |
| GET | /hr/salary/{salaryId} | 管理端工资详情 | hr:salary:query |
| POST | /hr/salary | 创建工资草稿 | hr:salary:add |

| GET | /hr/salary/options/employees | 分页查询员工候选 | hr:salary:add |

管理端查询、新增、编辑、发布及员工候选均仅允许 HR 和管理员访问。

不提供删除、撤回发布或修改已发布工资单接口。

### 12.2 管理端查询

列表参数：

- employeeId：员工筛选。
- salaryMonth：工资月份，格式 YYYY-MM。
- status：草稿或已发布。
- pageNum、pageSize。

固定按工资月份降序、salary_id 降序排列。

列表返回员工编号、工号、姓名、工资月份、四项组成金额、应发金额及状态。

详情增加发布人、发布时间和审计字段。不返回登录密码、账号配置或无关员工档案字段。

金额统一使用两位小数的十进制字符串。

### 12.3 创建草稿

请求字段：

- employeeId。
- salaryMonth。
- baseSalary。
- allowance。
- bonus。
- deduction。

四项金额均必填，使用十进制字符串。salaryMonth 必须严格符合 YYYY-MM，后端转换为当月第一天保存。

员工必须存在，允许为离职员工补录。相同员工、月份不能重复创建。

状态固定为草稿，应发金额由后端计算。

成功返回新 salaryId。

### 12.4 编辑与发布

编辑请求仅包含：

- baseSalary。
- allowance。
- bonus。
- deduction。

salaryId 从路径取得，员工和月份不可修改。

发布接口不需要请求正文。后端锁定工资行，检查草稿状态、金额和计算结果，再保存发布状态、发布人及时间。

编辑和发布都重新检查最新状态；已发布时拒绝操作。

### 12.5 本人查询

本人列表只接受 salaryMonth 和分页参数，不接受 employeeId 或发布状态筛选。

后端从当前登录账号关联的员工档案确定范围，并强制只查询已发布记录。

本人详情同时检查员工归属与发布状态；无权访问时返回“记录不存在或无权访问”。

没有关联员工档案时，提示“当前账号未关联员工档案”，不查询全公司记录。

本人响应包含月份、工资组成、应发金额和发布时间，不返回审计账号或内部管理字段。

### 12.6 员工候选

支持 keyword、pageNum、pageSize，按工号或姓名搜索。

返回 employeeId、employeeNo、employeeName、employmentStatus，包含在职及离职员工，供历史工资补录使用。

该接口仅用于选择工资归属，不返回员工备注或账号信息。

### 12.7 验收重点

- 没有工资管理权限的账号不能调用管理端接口。
- 员工不能通过构造 employeeId 查询他人工资。
- 客户端传入 payableAmount 或 status 不能改变计算结果和状态。
- 同一员工同月并发创建时，仅一条成功。
- 发布与编辑并发时，发布后内容不可修改。
- 查询与操作响应不暴露无关档案或账号信息。

## 13. 考勤接口

### 13.1 接口清单

管理端接口及员工候选仅允许 HR 和管理员访问。

本人接口要求账号关联员工档案；打卡另外检查在职状态。

不提供考勤删除接口。

### 13.2 查询参数和返回

管理端列表支持：

- employeeId。
- beginDate、endDate，格式 YYYY-MM-DD，包含首尾日期。
- pageNum、pageSize。

本人列表只接受日期范围和分页参数，不接受 employeeId。

起止日期均可省略；同时提供时，beginDate 不能晚于 endDate。列表固定按考勤日期降序、attendance_id 降序排列。

列表返回员工编号、工号、姓名、考勤日期、上班时间、下班时间及是否经过人工处理。

管理端详情增加最近更正人、时间、原因及审计字段。

本人详情返回考勤时间和更正原因，不返回管理账号名称及审计字段。

当天查询返回：

- businessDate：后端业务日期。
- serverTime：后端当前时间。
- clockState：NOT_CLOCKED、CLOCKED_IN、CLOCKED_OUT。
- attendanceId：无记录时为 NULL。
- clockInTime、clockOutTime：没有对应时间时为 NULL。
- canClockIn、canClockOut：根据档案状态和当天记录计算。

### 13.3 员工打卡

上下班打卡不需要请求正文，不接受员工编号、日期和时间。

后端根据登录账号取得员工档案，使用后端当前时间完成操作。

成功返回 attendanceId、attendanceDate、clockInTime、clockOutTime。前端随后刷新当天状态和本人列表。

重复打卡返回业务错误，不新增记录，也不覆盖原时间。

### 13.4 人工补录与更正

补录请求：

- employeeId。
- attendanceDate。
- clockInTime。
- clockOutTime，可为 NULL。
- correctionReason。

补录仅用于该员工该日没有记录的情况。已有记录时拒绝补录，提示使用更正操作，不隐式覆盖。

更正请求：

- clockInTime。
- clockOutTime，可为 NULL，表示清空。
- correctionReason。

更正目标从 attendanceId 路径取得，不接受修改员工编号或考勤日期。

校验规则沿用第 7 节。操作成功后返回成功提示，前端重新查询记录。

### 13.5 员工候选

参数为 keyword、pageNum、pageSize，按工号或姓名搜索。

返回 employeeId、employeeNo、employeeName、employmentStatus，包含在职和离职员工，以支持历史补录。

不返回备注、账号及其他无关信息。

### 13.6 验收重点

- 修改浏览器时间不影响后端打卡时间。
- 员工不能指定他人身份打卡。
- 当天无记录时，下班操作被拒绝。
- 并发打卡只产生一条当天记录。
- 人工补录不能覆盖已有记录。
- 更正必须填写原因，并记录操作日志。
- 负责人不能查看本部门其他员工考勤。

后端决定 employeeId、applicantUserId、deptId、approverUserId、approverType、leaveDays 和 status。

成功返回 leaveId。

账号没有关联员工档案、员工离职、日期重叠或审批配置无效时，拒绝提交并说明原因。

### 14.3 查询范围

本人列表：

- 强制按当前关联 employeeId 查询。
- 允许按类型、状态、请假日期范围筛选。
- 不接受 employeeId、deptId 或 approverUserId。

管理列表：

- HR 和管理员可以查看全公司。
- 部门负责人只查看提交时部门属于其当前有效负责人配置的申请。
- 普通员工不能访问。
- 支持 employeeId、deptId、类型、状态和请假日期范围筛选。
- 请求筛选条件必须与服务端允许范围取交集，不能扩大权限。

审批列表：

- 强制 approverUserId 为当前登录账号。
- 默认查询待审批，允许筛选已批准、已驳回或已撤回记录。
- 支持类型和请假日期范围筛选。
- 不接受其他审批账号或员工编号作为范围条件。

所有列表使用 pageNum、pageSize，固定按 create_time 降序、leave_id 降序排列。

日期范围筛选采用区间相交规则：申请结束日期不早于 beginDate，申请开始日期不晚于 endDate。任一边界可省略。

### 14.4 查询返回

列表返回：

- leaveId、employeeId、employeeNo、employeeName。
- deptId、deptName，使用申请保存的部门编号取得当前部门名称。
- leaveType、startDate、endDate、leaveDays、status。
- approverUserId、审批人显示名称。
- createTime。

详情增加请假原因、审批意见、审批时间和撤回时间。

不返回员工备注、工资、密码及无关账号信息。

部门名称和账号显示名称不是历史文本快照；相关名称变更后，页面显示当前名称。

三种详情入口分别检查本人范围、管理范围和指定审批账号，不互相替代。

### 14.5 批准与驳回

批准请求包含可选 approvalComment。

驳回请求包含必填 approvalComment，去除首尾空格后不能为空，最多 500 个字符。批准意见同样最多 500 个字符。

不接收 status、approverUserId 或 approvedTime。

后端在事务中锁定申请，检查指定账号、有效身份、禁止自审及待审批状态，再写入目标状态、意见、处理人和时间。

管理员不能通过管理端查询权限绕过指定审批人限制。

处理成功返回操作成功提示，前端刷新列表和详情。

### 14.6 撤回

撤回接口不需要请求正文。

后端检查：

- 当前账号等于提交时 applicantUserId。
- 当前账号仍关联申请的 employeeId。
- 申请处于待审批状态。

满足条件后保存已撤回状态和撤回时间。

离职不阻止撤回已有申请；账号解除关联或更换后，其他账号不能代替原申请账号撤回。

### 14.7 页面操作能力

详情响应增加后端计算的布尔字段：

- canWithdraw。
- canApprove。
- canReject。

计算依据包括当前账号、角色或身份、员工关联及申请状态。

这些字段帮助页面显示按钮，不替代操作接口的重新校验。

### 14.8 验收重点

- 修改请求中的身份、审批人或状态字段不能改变后端判断。
- 非指定账号不能审批，即使具有管理员权限。
- 原审批人可以查看分配记录，但失去有效审批身份后不能处理。
- 申请撤回与审批并发时，只能有一次有效状态变化。
- 调岗不改变已有申请的部门和审批人。
- 解除账号关联后，旧账号不能使用员工自助入口查看或撤回该员工申请。
- 指定审批人更换关联员工后，仍不能审批自己的员工档案申请。

- 列表提供需求中确定的筛选项、分页和操作结果提示。
- 员工新增、编辑使用一个表单弹窗；新增默认在职。
- 工资草稿可编辑；发布前弹出确认提示，说明发布后不可修改。
- 考勤补录和更正使用表单，原因必填。
- 请假提交前显示自然日天数，最终天数由后端计算。
- 批准前确认，驳回时填写原因。
- 操作提交期间禁用对应按钮，减少重复点击；后端仍处理并发和重复请求。

- 离职员工的打卡及新请假入口禁用，仍允许查询历史；实际操作由后端再次校验。

## 17. 事务与关联数据保护

### 17.1 事务边界

事务用于保证相关数据库修改一起成功或一起回滚，不包含前端操作。

| 操作 | 同一事务中的内容 |
|---|---|
| 员工新增、编辑 | 保存档案，必要时同步账号部门与岗位 |
| 审批配置维护 | 校验并保存负责人或全局配置 |
| 工资编辑、发布 | 锁定工资单，检查状态，更新金额或发布信息 |
| 打卡、补录、更正 | 锁定员工，检查并保存当日考勤 |
| 请假提交 | 锁定员工，检查日期重叠及审批配置，保存申请 |
| 请假审批、撤回 | 锁定申请，检查最新状态，保存处理结果 |

使用 Spring 事务管理。事务方法发生异常时回滚，不捕获异常后返回成功。

操作日志记录实际操作结果，不能代替业务数据的事务一致性。

### 17.2 统一锁顺序

使用数据库行锁，只锁定当前操作涉及的记录，不锁整张表。

涉及员工和账号时，统一先锁员工，再按账号 ID 升序锁定相关账号；解除关联、重新关联时包含原账号和新账号。

员工账号同步通过 Service 内部方法完成，不在事务中调用 HTTP 接口。

若依账号编辑入口对已关联员工的账号，不允许单独修改部门和岗位。检查及保存前锁定目标账号，并重新检查关联情况。

账号编辑入口不在锁定账号后再锁员工，避免形成相反锁顺序。

其他业务按以下约定处理：

- 工资编辑与发布锁定目标工资单。
- 考勤操作锁定员工后处理当天记录。
- 请假提交锁定员工后检查重叠。
- 请假审批及撤回锁定申请，不再反向锁员工。

部门负责人配置变更与员工归属修改都需要锁定涉及的员工，并在锁定后重新检查资格。

配置角色或账号状态发生变化时，在提交、审批等操作中重新检查。账号停用后的会话失效处理沿用若依机制，并在业务入口核验账号当前启用状态。

本版本不保证管理员修改角色或审批配置与正在进行的请求瞬间同步；已进入事务且通过校验的操作可能完成，后续操作采用最新有效配置。

### 17.3 数据库约束与业务校验

业务层提前校验，提供明确提示；数据库约束作为最后保障。

必须保留：

- 工号唯一。
- 员工关联账号唯一。
- 员工与工资月份组合唯一。
- 员工与考勤日期组合唯一。
- 关联外键及字段合法性约束。

重复数据、外键限制等可预期冲突转为业务错误。未识别的异常记录到后端日志，页面不显示内部数据库信息。

请假日期重叠和角色有效性属于业务规则，不能仅依赖数据库外键。

### 17.4 关联资料删除保护

使用新增业务表的外键，阻止直接删除被引用的员工、账号、部门和职位。

若依已有部门、岗位、账号删除入口需增加人事关联检查：

- 部门：检查员工档案、部门负责人配置及请假提交时部门引用。
- 岗位：检查员工档案引用。
- 账号：检查员工关联、审批配置、申请人及审批人引用。

发现引用时，提示先调整关联或使用停用操作，不执行级联删除。

删除检查必须在原有删除事务中完成。若并发产生引用，数据库外键仍应阻止删除，并返回可理解的提示。

员工档案、工资、考勤、请假不提供物理删除接口。

### 17.5 初始化与迁移

新增业务使用独立增量 SQL，按以下顺序创建：

1. 员工档案。
2. 部门负责人配置、全局审批配置。
3. 工资、考勤、请假。
4. 业务角色、菜单及权限关联。

不修改原有初始化脚本，不在业务 SQL 中保存真实密码。

角色和菜单编号需根据现有数据选择未占用编号，不能假定某段编号为空。

业务管理员、HR、负责人和员工的演示账号通过若依页面建立，并明确记录操作步骤。演示员工和审批配置同样通过业务页面建立，避免依赖预设账号 ID。

数据库脚本记录执行顺序和适用版本，不宣称可以任意重复执行。
